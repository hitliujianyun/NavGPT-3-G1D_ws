## 1. 总体部署拓扑与选择

```
┌──────────── 上位机 Ubuntu 24.04 · 双 RTX 5090 ────────────┐        ┌──────────── G1-D · PC2 (Jetson) ─────────────┐
│ GPU0: serve_vla.py :8100  (NavGPT3-8B, 推理)                │  Wi-Fi │ navgpt_g1d serve :8124                         │
│ GPU1: navgpt_sft 训练 / 其他模型                            │◀──────▶│   推理线程 ──HTTP──▶ :8100                      │
│ 可选: Web 界面 / Planner → 调用 PC2 :8124                   │        │   控制线程 20 Hz ─▶ CmdVelStreamer 30 Hz        │
└────────────────────────────────────────────────────────────┘        │ DDS(内部以太网): odom / scan / cmd_vel_no_limit │
                                                                      │ teleimager :55555 (头部相机)                   │
                                                                      └───────────────────────────────────────────────┘
```

**推荐方案 A：`navgpt_g1d` 跑在 PC2 上。** 20 Hz 控制、里程计、激光安全、底盘指令发布全部留在机器人本地；Wi-Fi 抖动只影响“新预测多久来一次”，由路径缓冲（约 1 m）和断供降速吸收，不会直接造成底盘指令断续。

**备选方案 B：`navgpt_g1d` 跑在上位机上，DDS 走 Wi-Fi。** 只在 PC2 环境装不起来时临时使用。这时 30 Hz 的 `cmd_vel_no_limit` 要穿过 Wi-Fi，丢包会被 0.3 s 的死人开关变成急停，CycloneDDS 的组播在 Wi-Fi 上也不可靠。必须做的调整见 [5.6](#56-备选方案-b在上位机上运行时的额外调整)。

> 不需要做跨机时钟同步：相机帧和里程计都在 PC2 本机用同一个单调时钟打时间戳；拍照时刻的位姿在 PC2 上记录，随请求带出、随回复带回。

## 2. 5090 主机：驱动、CUDA 与 Python 环境

### 2.1 驱动

- RTX 5090 是 Blackwell 架构（compute capability 12.0，`sm_120`），需要 **NVIDIA 驱动 ≥ 570**，并使用 **open 内核模块**（Ubuntu 上为 `nvidia-driver-570-open` 或更新版本）。
- 检查：

```bash
nvidia-smi                                   # 驱动版本 ≥ 570，两张卡都可见
nvidia-smi --query-gpu=index,name,compute_cap,memory.total --format=csv
```

### 2.2 PyTorch 版本：必须偏离官方锁定

| 项 | 官方 NavGPT-3 | 5090 上 |
|---|---|---|
| PyTorch | `torch>=2.6,<2.7`，cu124 | **torch 2.7.1 + cu128**（2.7 起才有 sm_120 内核） |
| torchvision | 0.21 | 0.22.1 |
| transformers | `==5.18.0` | **保持 5.18.0 不变**（NavGPT3 继承其 Qwen3-VL 类，并复原了特定版本的位置编码算术） |
| flash-attn | 可选 2.7.4 | 预编译包不一定支持 sm_120；**不装也可以，代码自动用 SDPA** |

`scripts/setup_gpu_server.sh` 已经处理好了：它按 `nvidia-smi` 报告的 compute capability 自动选择版本，安装其余依赖时跳过 `requirements-vla.txt` 里的 torch 版本约束，把训练包和 PEFT 装进同一个 VLA 环境，最后做一次 GPU 自检。

```bash
# Ubuntu 24.04 的系统 Python 是 3.12，且受 PEP 668 保护，不要往系统 Python 里 pip install；用 uv
curl -LsSf https://astral.sh/uv/install.sh | sh
git clone --recurse-submodules https://github.com/hitliujianyun/NavGPT-3-G1D_ws.git
cd NavGPT-3-G1D_ws
bash scripts/setup_gpu_server.sh            # 需要仿真评测时：WITH_HABITAT=1 bash scripts/setup_gpu_server.sh
```

自检输出应包含：`torch 2.7.1+cu128`、`device NVIDIA GeForce RTX 5090 sm_120 supported: True`、`bf16 matmul ok: True`。

### 2.3 偏离官方版本后的数值核对（建议做一次）

官方权重是在 torch 2.6 / transformers 5.18 下验证的。换成 torch 2.7 后，建议用固定输入对比 GPU 和 CPU 的输出。CPU 端可以在任何机器上运行，包括装着官方 torch 2.6 的环境：

```python
# check_numerics.py —— 在 code/NavGPT-3/.envs/vla 里运行：python check_numerics.py cuda / cpu
import functools, random, sys
import numpy as np
import navgpt.vla.agent as A
from navgpt.vla.runtime.inference import load_from_pretrained

device = sys.argv[1]
A.load_from_pretrained = functools.partial(load_from_pretrained, device=device)
agent = A.NavGPTVLA("models/NavGPT3-4B", view_num=1, frame_cache="on_demand", attn_implementation="sdpa")
rng = np.random.default_rng(0)
images = [rng.integers(0, 255, (400, 400, 3), dtype=np.uint8) for _ in range(6)]
random.seed(0)
for im in images[:-1]:
    agent.observe_history([im])
print(np.round(agent.act([images[-1]], "Walk forward and stop at the door."), 4).tolist())
```

两边的 8 个航点逐项相差应在几厘米、几度以内（bf16 舍入）。如果差距很大，先怀疑 transformers 版本被升级了，或者注意力实现不同。

### 2.4 模型权重

```bash
bash scripts/download_weights.sh 8B 4B      # 下载到 models/NavGPT3-8B、models/NavGPT3-4B
# 访问 Hugging Face 慢时可设置镜像：export HF_ENDPOINT=https://hf-mirror.com
```

权重为 **AGPL-3.0**；基于它微调出的权重同样受约束，对外分发或提供服务前需要评估。

## 3. 5090 主机：VLA 推理服务

### 3.1 启动与 GPU 分配

```bash
CHECKPOINT=models/NavGPT3-8B GPU=0 PORT=8100 deploy/g1d/scripts/start_vla_server.sh --attn-implementation sdpa
```

| 项 | 建议 |
|---|---|
| 模型 | 推理用 **8B**（BF16 约 17.6 GB，单张 32 GB 的 5090 放得下）；论文中 8B 比 4B 的 R2R-CE 成功率高约 2.6 个点 |
| 双卡分工 | GPU0 固定给 VLA 服务；GPU1 给训练或其他模型（例如你现有的 InternVLA），互不抢占 |
| 端口 | 默认 8100，避开你现有服务占用的 8000/8010（VLA）和 8123（Web） |
| 预热 | 启动时自动做 3 次假推理再 reset，第一次真实请求不会变慢；日志里的 `warm-up inference` 就是单步推理耗时的参考值 |
| 并发 | 服务有状态、所有请求串行处理，**一次只服务一台机器人、一个任务** |

### 3.2 开机自启（systemd）

```ini
# /etc/systemd/system/navgpt-vla.service
[Unit]
Description=NavGPT3 VLA service for G1-D
After=network-online.target

[Service]
User=<你的用户名>
WorkingDirectory=/home/<你的用户名>/NavGPT-3-G1D_ws
Environment=CHECKPOINT=models/NavGPT3-8B GPU=0 PORT=8100
ExecStart=/usr/bin/bash deploy/g1d/scripts/start_vla_server.sh --attn-implementation sdpa
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now navgpt-vla
journalctl -u navgpt-vla -f
```

### 3.3 防火墙

```bash
sudo ufw allow from <PC2 的 Wi-Fi 网段>/24 to any port 8100 proto tcp
```

## 4. 网络与 Wi-Fi

### 4.1 两个网段，各走各的

- PC2 有两块网卡：**内部以太网**（192.168.123.164，连 MCU、slamware、teleimager）和 **Wi-Fi**（连上位机）。
- **DDS 必须绑在内部以太网上**，否则 CycloneDDS 可能把 odom/cmd_vel 流量发到 Wi-Fi 上。在 `config/g1d.yaml` 里设置：

```yaml
dds:
  interface_ip: 192.168.123.164      # 按 IP 绑定，比按网卡名更可靠（与你现有 backend.py 的做法一致）
vla:
  url: http://<上位机在 Wi-Fi 网段的 IP>:8100
```

- 上位机和 PC2 的 Wi-Fi IP 建议在路由器上做 DHCP 保留，或者配成静态 IP。

### 4.2 Wi-Fi 质量要求与测试

| 指标 | 目标 | 测法 |
|---|---|---|
| 往返延迟 | 平均 < 10 ms，p95 < 50 ms | `ping -c 200 <上位机IP>` |
| 带宽 | > 20 Mbit/s 稳定 | `iperf3 -s`（上位机）/ `iperf3 -c <上位机IP> -t 30`（PC2） |
| 推理往返 | `latency_p95_s` ≲ 推理耗时 + 0.1 s | 跑一次任务后看 `navgpt_g1d report` |

每次请求上传一张 400×400 的 JPEG（质量 85，约 30–50 KB），按 1–3 Hz 计算不到 1.5 Mbit/s。建议使用 **5 GHz 专用 AP**，关闭 AP 的省电和漫游策略；Web 界面的 MJPEG 全画面预览和腕部相机流不要和推理抢带宽，调试时再打开。

## 5. 机器人侧（PC2）：安装与配置

### 5.1 确认系统环境

```bash
cat /etc/nv_tegra_release; python3 --version      # navgpt_g1d 需要 Python ≥ 3.8
```

`navgpt_g1d` 只依赖 numpy、pyyaml、requests、pyzmq、OpenCV 和 unitree_sdk2py，**不需要 torch，也不需要 GPU**。训练包 `navgpt_sft` 需要 Python ≥ 3.10，只在上位机上用。

### 5.2 安装

```bash
git clone --recurse-submodules https://github.com/hitliujianyun/NavGPT-3-G1D_ws.git
cd NavGPT-3-G1D_ws

# 1) unitree_sdk2_python：需要先编译安装 CycloneDDS 0.10.x，并设置 CYCLONEDDS_HOME（见其 README）
#    如果 PC2 上你现有的 chassis_control_ws 已经能用 unitree_sdk2py，就沿用同一个环境
pip3 install -e code/unitree_sdk2_python

# 2) navgpt_g1d：Jetson 上一般已有系统 OpenCV，避免再装 opencv-python 冲突
pip3 install pyzmq
pip3 install -e deploy/g1d             # 若系统没有 OpenCV：pip3 install -e "deploy/g1d[robot]"
python3 -c "import cv2, zmq, unitree_sdk2py; print('ok')"
```

### 5.3 teleimager（头部相机）

- PC2 上要运行 `teleimager-server`（你现有系统已经在用）。确认头部相机的 ZMQ 端口：`python -m teleimager.image_client --host 192.168.123.164` 会打印各相机的端口表。`navgpt_g1d` 默认用 **55555**，如果不同，改 `camera.port`。
- `camera.binocular: true` 对应 480×1280 的左右拼接帧；代码取左半幅 → 居中裁成方形 → 缩放到 400×400，与训练分辨率一致，也和训练工程要求的数据预处理一致。

### 5.4 话题与消息类型（逐项核对）

| 配置项 | 默认值 | 核对方法 |
|---|---|---|
| `topics.odom` | `rt/slamware_ros_sdk_server_node/odom`（`nav_msgs/Odometry_`） | `navgpt_g1d check` 显示 `odom_hz` 约 10 |
| `topics.scan` | `rt/slamware_ros_sdk_server_node/scan` | `check` 显示 `scan_hz` 约 10、`scan_points` 约 360 |
| `topics.cmd_vel` | `rt/cmd_vel_no_limit`（`geometry_msgs/Twist_`） | `smoke` 能让底盘按预期移动 |

> **LaserScan 消息定义要特别核对。** unitree_sdk2py 没有 LaserScan，`navgpt_g1d/laserscan_idl.py` 是按 ROS 2 标准字段补的，typename 为 `sensor_msgs.msg.dds_.LaserScan_`。你现有系统里也有一个自带的 `laserscan.py`。如果 `check` 显示 `scan_hz` 为 0，把两者的 typename 和字段顺序对齐，或者直接改用你那份已经验证过的定义。实在对不上时，可临时设 `safety.enabled: false` 先调通其余部分，但**这样就没有激光保护**，只能在空场地、有人手持遥控急停的情况下测试。

### 5.5 `config/g1d.yaml` 中必须实测填写的项

| 项 | 怎么得到 |
|---|---|
| `dds.interface_ip` | PC2 内部以太网的 IP（一般是 192.168.123.164） |
| `vla.url` | 上位机在 Wi-Fi 网段的地址 + 8100 |
| `base.cmd_x_sign` / `cmd_yaw_sign` / `odom_yaw_sign` | 先抄你现有 `backend.py` 里已验证过的值，再用 `navgpt_g1d smoke` 复核 |
| `safety.lidar_x_m` / `lidar_y_m` / `lidar_yaw_rad` | slamware 激光在底盘坐标系里的安装位置（可以看 slamware 的 TF，或者实测） |
| `safety.front_m` | 激光中心到前保险杠的距离（卷尺量） |
| `safety.min_range_m` | 打开 `check`，看静止空旷时最近的回波是否来自机身；把它设在机身回波之外 |
| `camera.latency_s` | 拍照到 PC2 收到帧的延迟。粗测：原地以恒定角速度旋转，看日志中 VLA 首个航点方向与实际朝向的系统性滞后；默认 0.06 s 通常够用 |
| `tracker.v_max` | 先 0.2–0.3 m/s；稳定后按 `v_max ≲ 0.25 m × 实测推理频率` 逐步提高 |

### 5.6 备选方案 B：在上位机上运行时的额外调整

- **CycloneDDS 改单播**：Wi-Fi 上组播不可靠。写一个 CycloneDDS XML，`<General><Interfaces>` 绑定上位机的 Wi-Fi 网卡，`<Discovery><Peers>` 列出 PC2 的 IP，关闭组播（`AllowMulticast=false`），并通过 `CYCLONEDDS_URI` 指定；此时 `dds.interface_ip` 填上位机的 Wi-Fi IP。机器人侧（PC2 或 MCU 上发布 odom 的节点）也要能单播到上位机，可能需要在 PC2 上做 DDS 桥接。
- **放宽死人开关**：`base.cmd_timeout_s` 从 0.3 提到 0.5，同时接受偶发急停。
- **相机流走 Wi-Fi**：teleimager 的整帧 1280×480 JPEG 会以 30 fps 跨 Wi-Fi 传输，带宽占用远大于方案 A。
- 结论：方案 B 只适合联调，正式运行请用方案 A。

## 6. 上机验证流程

按顺序执行，每一步通过再进入下一步：

```bash
# 0) 任意机器：全链路仿真，确认代码和依赖正常
cd deploy/g1d && python3 -m unittest discover -s tests && python3 -m navgpt_g1d sim --route L --crossing

# 1) PC2：传感器与 VLA 连通
python3 -m navgpt_g1d check --config config/g1d.yaml --seconds 5
#    期望：odom_hz≈10，scan_hz≈10，camera_hz≈30，frame=[400,400,3]，VLA reachable，往返 < 50 ms

# 2) PC2：底盘方向（周围清空 1.5 m，遥控器在手）
python3 -m navgpt_g1d smoke --config config/g1d.yaml
#    按提示观察实际运动方向，程序给出 cmd_x_sign / cmd_yaw_sign / odom_yaw_sign 的修改建议

# 3) PC2：空跑（除了不发 cmd_vel，其余全真）
python3 -m navgpt_g1d run --config config/g1d.yaml --dry-run --instruction "Walk forward and stop at the door."
python3 -m navgpt_g1d report logs/<时间戳>      # 看 latency、replies、committed_frames、deviation

# 4) PC2：低速实跑（v_max 0.2，空旷走廊，直行到门口）
python3 -m navgpt_g1d run --config config/g1d.yaml --instruction "Walk forward and stop at the door."

# 5) 常驻服务，供 Web 界面 / Planner 调用
deploy/g1d/scripts/start_robot.sh
curl -X POST http://<PC2 Wi-Fi IP>:8124/episode -d '{"instruction": "Go to the trash can."}'
curl http://<PC2 Wi-Fi IP>:8124/status
```

**每次实跑后看 `report` 的这几项：**

| 指标 | 合格线（建议） | 不合格时先查 |
|---|---|---|
| `stall_ratio` | < 3% | `latency_p95_s`、`phase_s` 里断供 / 恢复的时长 |
| `max_accel_mps2` | ≤ `a_max`/`a_dec` | 控制循环是否卡顿（看 `control_hz` 是否 ≈ 20） |
| `latency_p95_s` | < 推理耗时 + 0.15 s | Wi-Fi、JPEG 质量、服务端是否被其他进程占用 |
| `splice_deviation_p95_m` | < 0.3 m | 模型前后预测抖动大：检查相机画面与训练分布是否差异大，考虑微调 |
| `accepted_ratio` | > 0.95 | 回复太慢被判过期（`max_reply_age_s`），或频繁保护停止 |

## 7. 需要补强的代码与已知差距

### 7.1 里程计跳变（建议上线前补上）

参考路径锚定在里程计坐标里。如果 slamware 的 odom 话题输出的是**会因重定位而跳变**的地图位姿，已锚定的路径会整体错位，机器人可能突然转向。先确认：静止时观察 `check` 输出的 `odom_pose`，推着机器人走一圈，看有没有突跳。

如果有跳变，有两种处理方式：
1. 优先改用连续的里程计话题（轮式里程计，或 slamware 的 odom 坐标系输出）。
2. 在 `episode.py` 的控制循环里检测跳变，检测到就丢弃旧路径和跳变前拍摄的帧，用新鲜预测重新开始：

```python
# episode.py 控制循环中，取得 latest 之后（示意）
if prev_odom is not None:
    (t0, p0), (t1, p1) = prev_odom, latest
    if t1 > t0 and math.hypot(p1[0] - p0[0], p1[1] - p0[1]) > 0.2 + 1.0 * (t1 - t0):   # 远超底盘能力
        with lock:
            nav.resume(now)          # 只接受此后拍摄的帧；非最终路径清空、速度归零
        log.write("odom_jump", jump_m=math.hypot(p1[0] - p0[0], p1[1] - p0[1]))
prev_odom = latest
```

`Navigator.resume` 已经具备所需的语义：丢弃此前拍摄的帧的回复、清空非最终路径、速度从零按加速度限幅起步。

### 7.2 训练数据采集工具（缺）

训练工程需要遥操作示范：稠密帧，以及拍照时刻的里程计位姿。目前仓库里**没有录制工具**，只有从自主运行日志转换的 `from-g1d-logs`。建议在 `navgpt_g1d` 里增加一个 `record` 子命令：复用 `HeadCamera` 和 `OdomSubscriber`，以 3–5 Hz 保存 `camera.preprocess` 处理后的 400×400 图像，以及 `PoseBuffer.at(t_rx − latency_s)` 的位姿，直接写成 `navgpt_sft` 的 manifest 格式。遥控器负责驾驶，不发 `cmd_vel`。

### 7.3 Planner 集成接口（部分缺）

HTTP 接口目前有 `/episode`、`/stop`、`/status`，可以覆盖 Planner 的 `navigate_by_instruction`（启动一段 VLA 执行并轮询结果）。你的 PlannerRunner 里的 `navigate_relative`（原地转 + 直行）、`/observe`（把修复过程中经过的帧补进 VLA 历史）还**没有对应接口**；需要的话，可以在 `api.py` 里加一个 `/relative`，把相对位姿转成一条参考路径，交给同一个跟踪器执行。

### 7.4 其他

| 项 | 现状 | 建议 |
|---|---|---|
| 服务端 `commit=false` 与预热 | 没有加载真实模型测过 | 在 5090 上跑一次 `dry-run`，看 `reply` 事件里的 `frames` 是否只在提交时增长 |
| 相机端口自动发现 | 固定使用 `camera.port` | 需要的话可以改成先向 teleimager 的 60000 端口请求配置 |
| 安全层只看前方 | 不做绕行 | 持续阻挡交给 VLA 的下一次预测或 Planner；卡住超过 4 s 判 `stuck` |
| 底盘自身的碰撞 / 低矮障碍传感器 | 未接入软件 | 保持底盘自带的保护开启，作为最后一道防线 |

## 8. 与现有系统共存与集成

- **同一时刻只能有一个程序发布 `rt/cmd_vel_no_limit`。** 运行 `navgpt_g1d` 时，停掉你现有的 EpisodeRunner / PlannerRunner 的底盘后端（`g1d_nav_chassis.backend`），避免两路速度指令互相覆盖。`navgpt_g1d` 只在任务期间发布，结束时零速保持 1 s 后释放，遥控器可以接管。
- **复用现有 VLA 服务**：`vla_client.py` 兼容 `{"navigation": [...]}` 应答，可以把 `vla.url` 指向你现有的 :8000 服务做对比测试。但它会忽略 `commit` 参数，每一帧都进历史，帧会比训练时密。正式运行建议用 `serve_vla.py`。
- **Web 界面**：你现有的 Web（:8123）可以调用 PC2 的 :8124 接口启动、停止任务，读取 `/status` 做实时显示。接口的响应带了 `Access-Control-Allow-Origin: *`，浏览器可以直接跨域 GET；但浏览器直接 POST JSON 会先发 OPTIONS 预检，`api.py` 目前不处理预检。最简单的做法是由 Web 后端（stdlib HTTP 服务）转发 POST，或者在 `api.py` 里补一个 `do_OPTIONS`。
- **方向符号**：直接沿用你现有 backend 已验证过的 `cmd_x_sign` / `cmd_yaw_sign` / `odom_yaw_sign`，再用 `smoke` 复核。

## 9. 5090 上的训练

```bash
# 训练在 GPU1，避免影响 GPU0 上的推理服务
export CUDA_VISIBLE_DEVICES=1
PY=code/NavGPT-3/.envs/vla/bin/python
$PY -m navgpt_sft inspect --config train/configs/g1d_lora_4b.yaml
$PY -m navgpt_sft eval    --config train/configs/g1d_lora_4b.yaml                                   # 基线
$PY -m navgpt_sft train   --config train/configs/g1d_lora_4b.yaml
$PY -m navgpt_sft eval    --config train/configs/g1d_lora_4b.yaml --adapter outputs/sft/g1d_lora_4b/checkpoint-<N>
$PY -m navgpt_sft merge   --config train/configs/g1d_lora_4b.yaml --checkpoint outputs/sft/g1d_lora_4b/checkpoint-<N> --out models/NavGPT3-4B-g1d
```

| 项 | 说明 |
|---|---|
| 显存 | 4B、batch 1、梯度检查点，单张 5090 可以训；8B 在 32 GB 上很紧，建议先训 4B |
| 双卡训练 | 推理服务停掉时，可以 `accelerate launch --num_processes 2 -m navgpt_sft train ...` 用两张卡（DDP，每卡一份完整模型） |
| 端到端测试 | 本机跳过的 `train/tests/test_pipeline.py` 需要在 5090 的 VLA 环境里跑一次。它还需要 Qwen3-VL 的 tokenizer/processor 文件放在 `models/_qwen3vl_tok`（下载方法见 `tests/tiny_checkpoint.py`） |
| 上线微调模型 | `CHECKPOINT=models/NavGPT3-4B-g1d deploy/g1d/scripts/start_vla_server.sh`，部署代码不用改 |
| 一致性 | `train/configs/*.yaml` 的 `nav.keyframe_m/rad`、`nav.scale`、预算参数必须和 `deploy/g1d/config/g1d.yaml`、`serve_vla.py` 的参数一致 |

## 10. 模型与场景适配

| 差距 | 影响 | 处理 |
|---|---|---|
| 头部相机视场角（训练为 120°） | 视场角窄时物体显得更近，航点尺度可能偏差 | 实测视场角；差距大时考虑加装 120° 广角相机，或用 G1-D 数据微调 |
| 相机高度（仿真为 1.25 m） | 视角差异 | 调节立柱，让头部相机接近 1.25 m |
| 单目输入（论文主结果用四视角） | codec 增益基本消失（单视角下预算/容量比约 0.98），缺侧后方信息 | 先用单目；需要时改为四目，`serve_vla.py` 和训练配置的 `view_num` 同步改成 4 |
| 指令语言 | 只在英文上评测过 | 实机先用英文；中文需要翻译步骤，或积累足够的中文训练数据 |
| 真实场景外观 | 仿真到真实的分布偏移；论文 Go2 上仅用 VLA 的成功率为 60% | 采集现场数据，用 `navgpt_sft` 微调 |
| 玻璃门、行人、低矮障碍 | RGB 模型难以感知 | 依赖激光安全层和底盘自带的保护 |

## 11. 安全清单

- [ ] 首次上机时遥控器在操作员手中，并确认遥控器能抢占底盘（任务结束后通道会释放）
- [ ] `smoke` 确认前后、左右方向正确后，才允许 `run`
- [ ] `check` 显示激光正常（`scan_hz` 约 10），`safety.enabled: true`
- [ ] 在机器人前方放纸箱测试：慢慢推近时机器人先减速，进入停止区立即停止，移开 1 s 后自动恢复
- [ ] 拔掉 Wi-Fi 或停掉 VLA 服务：机器人 1.5 s 后降速，3 s 后停车；连续失败 10 次后任务以 `error` 结束并释放底盘（每次请求超时 4 s，Wi-Fi 完全断开时约 40 s 后才结束，期间机器人保持停止）
- [ ] 让控制循环卡住（例如在调试器里暂停）：0.3 s 死人开关后 `CmdVelStreamer` 改发零速，底盘停止
- [ ] 直接杀掉 `navgpt_g1d` 进程：此时不再有任何指令发出，底盘是否自动停车取决于底盘固件对“收不到 cmd_vel”的处理，必须实测；如果底盘会保持最后一条速度，就要依赖遥控器急停
- [ ] 底盘自带的碰撞传感器和低矮障碍传感器保持开启
- [ ] `v_max` 从 0.2 m/s 起步，在空旷场地验证后再逐步提高
